# Enum Value Resolution Delivery Document (Historical)

> **⚠️ Note:** The Rust dumper (dump phase) described in this document has been rewritten in Go.
> The Rust `hotech-evtx` crate now handles parsing only. The message database is generated by [msgdb-dump](https://github.com/kitsch-9527/msgdb-dump) (binary `msgdb-dump`). This document is kept for historical reference.

> Three-phase implementation: standard type conventions + CRIM VMAP/BMAP parsing + full pipeline integration.
> Last updated: 2026-07-07

---

## 1. What Was Implemented (3 Phases)

### Phase 1: Standard Type Convention Enum Resolution (win:Boolean)

A lightweight, no-DB heuristic layer that catches boolean-typed fields by name pattern before substitution.

**Functions added in `substitute.rs`:**
- `resolve_enum(value, field_name)` — resolves raw `"0"`/`"1"` to `"Disabled"`/`"Enabled"` when field name matches boolean heuristics
- `apply_param_enums(params, param_map)` — applies `resolve_enum` across the entire parameter vector using the `parameters` map from `MessageRow`
- `is_boolean_field(name)` — detects Hungarian-style boolean names (`is*`, `has*`, `can*`, `will*`, `should*`, `*Enabled`, `*Disabled`, `*Active`, `*Flag`, `*State`, `*Bool`)

**Coverage:** Handles `win:Boolean` convention only. No database dependency, no provider-specific knowledge.

### Phase 2: CRIM VMAP/BMAP Parsing + value_maps MSG DB Schema

Full PE-to-DB pipeline for extracting and persisting enum value maps from CRIM blocks.

**Functions added in `extractor.rs`:**
- `parse_vmap_block(crim_data, pos)` — parses CRIM `VMAP` blocks (u32 value to UTF-16 display name) into `HashMap<u32, String>`
- `parse_bmap_block(crim_data, pos)` — parses CRIM `BMAP` blocks (u64 bit position to UTF-16 display name) into `HashMap<u64, String>`
- Dispatch in `parse_crim_provider_data()`: recognises `VMAP` and `BMAP` block signatures alongside existing EVNT/TASK/OPCO/LEVL/KEYW/TTBL
- `CrimProviderData.value_maps` and `CrimProviderData.bit_maps` fields

**Schema added in `writer_sys.rs`:**
- `CREATE_VALUE_MAPS_TABLE` DDL constant
- `insert_value_maps()` — writes VMAP entries to `value_maps` table
- `insert_bit_maps()` — writes BMAP entries to `value_maps` table with `is_bitmap=1`

### Phase 3: Value Maps Integration in Substitution Pipeline

Connects the persisted data from Phase 2 into the runtime resolution engine.

**Functions added in `resolver.rs`:**
- `MessageDb::load_value_maps()` — loads all rows from `value_maps` table into in-memory `HashMap<String, HashMap<String, String>>` (graceful if table does not exist)
- `MessageDb::get_value_map(map_name, value)` — single-entry lookup
- `MessageDb::get_param_value_maps(param_map)` — fetches relevant value maps for specific field names (used in parallel batch to minimise cloned data per event)
- `MessageDb::resolve_value(provider, map_name, raw_value)` — raw u32 to display name via in-memory cache
- `MessageDb::has_value_maps()` — check if cache is populated

**Function added in `substitute.rs`:**
- `apply_value_maps(params, param_map, value_maps)` — replaces raw parameter values with display names using CRIM VMAP/BMAP entries, matching each parameter's field name to a map name

**Wiring in `cmd_dump.rs`:**
- Extracts `value_maps`/`bit_maps` from `CrimProviderData` during PE dump
- Converts u32/u64 keys to string keys for SQLite storage
- Writes `value_maps` table to messages.db after provider data

**Wiring in `cmd_parse.rs`:**
- Calls `db.load_value_maps()` during initialisation
- In `process_parallel_batch()`: brief lock to clone `MessageRow` + fetch relevant value maps via `get_param_value_maps()`
- Applies two-layer resolution: `apply_param_enums()` (Layer 1) then `apply_value_maps()` (Layer 2)

## 3. Schema Changes

### New table: `value_maps`

```sql
CREATE TABLE IF NOT EXISTS value_maps (
    provider_name TEXT NOT NULL,
    map_name      TEXT NOT NULL,
    entry_value   TEXT NOT NULL,
    display_name  TEXT NOT NULL,
    is_bitmap     INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (provider_name, map_name, entry_value)
);
```

**Design notes:**
- `entry_value` stored as `TEXT` (string form of the u32/u64 key) for string-keyed lookup in the in-memory hashmap
- `is_bitmap = 1` for BMAP entries (bit-position key), `is_bitmap = 0` for VMAP entries (integer value key). Both stored in the same table for unified querying.
- `provider_name` allows per-provider scoping. The current in-memory cache merges all providers by `map_name` (known limitation).
- `INSERT OR IGNORE` handles duplicate entries idempotently.

### Resolver in-memory cache

```rust
// In MessageDb struct:
value_maps: HashMap<String, HashMap<String, String>>
//                    map_name   entry_value -> display_name
```

Loaded from DB via `load_value_maps()` which queries all rows and builds the nested map. Only the relevant subset (matched by field name) is cloned per event in the parallel batch to minimise lock-contention data transfer.

## 4. Data Flow

### Dump Phase (messages.db population)

```
PE file (*.dll)
  |
  +-- pelite: extract_all_from_pe()
  |
  +-- RT_MESSAGETABLE  -> event message templates (-> dll_messages table)
  +-- RT_VERSION       -> PE version (-> dll_entries.pe_version)
  +-- WEVT_TEMPLATE resources -> raw CRIM binary blobs
       |
       +-- parse_crim_provider_data(crim_data, guid)
            |
            +-- EVNT  -> event metadata (-> dll_messages level/task/opcode/keywords)
            +-- TASK  -> task names         (resolved at parse time)
            +-- OPCO  -> opcode names       (resolved at parse time)
            +-- LEVL  -> level names        (-> level_name column)
            +-- KEYW  -> keyword names      (-> keywords_name column)
            +-- TTBL  -> template parameter names (-> parameters column)
            +-- VMAP  -> value_maps          {LogonType: {2 -> "Interactive"}}
            +-- BMAP  -> bit_maps            {AccessMask: {0 -> "Read", 1 -> "Write"}}
                                    |
                                    +-- insert_value_maps() / insert_bit_maps()
                                         -> INSERT INTO value_maps (...)
```

### Parse Phase (event resolution)

```
EVTX file -> parsed events with JSON event_data (raw numeric values)
  |
  +-- MessageDb.open(msg_db_path)
  +-- MessageDb.load_param_refs()      <- %%N expansion (prior work)
  +-- MessageDb.load_value_maps()      <- VMAP/BMAP entries into memory
  |
  +-- process_parallel_batch()
       |
       +-- warmup() -> batch-load MessageRows from messages.db
       |
       +-- per event (par_iter_mut, dual-phase resolution):
            +-- [brief lock] clone MessageRow + get_param_value_maps()
            +-- extract_subst_params()      -> params[0..N] from JSON
            +-- apply_param_enums()         -> Layer 1: win:Boolean heuristics
            +-- apply_value_maps()          -> Layer 2: CRIM VMAP/BMAP lookup
            +-- substitute()                -> fill template with resolved params
            +-- copy metadata (task, opcode, keywords, level_name)
```

### Resolution Priority

For each positional parameter `%N`:

1. Extract raw value from event XML/JSON (e.g. `"2"`)
2. Layer 1 (standard types): Is the field a `win:Boolean`? If yes, `"1"` to `"Enabled"`, `"0"` to `"Disabled"`. Otherwise pass through.
3. Layer 2 (CRIM maps): Does a value map named after this field contain this value? If yes, replace with the display name (e.g. `LogonType` -> `"2"` -> `"Interactive"`).
4. No match at either layer keep raw value.

Layer 2 runs after Layer 1, so the standard type convention acts as a first pass and CRIM VMAP entries can override it for specific fields.

## 5. What's Covered

| Scenario | Layer | Mechanism | Example |
|----------|-------|-----------|---------|
| Boolean fields (`is*`, `has*`, `*Enabled`) | Layer 1 | `resolve_enum()` heuristic | `isRoaming=1` to `"Enabled"` |
| CRIM VMAP integer enums (LogonType, SubStatus) | Layer 2 | `value_maps` table + `apply_value_maps()` | `LogonType=10` to `"RemoteInteractive"` |
| CRIM BMAP bitmask entries (stored, simple lookup) | Layer 2 | Same table, string-keyed HashMap::get | `AccessMask=1` to `"Read"` |
| %%N parameter refs | Prior work | `expand_param_refs()` + `parameter_refs` table | `%%14592` to `"SUCCESS"` |
| MSG DB driven full pipeline | Both | All data from messages.db via `hotech-evtx dump` | Graceful degradation if DB unavailable |

### CRIM VMAP Binary Format

```
+0: "VMAP" (4 bytes)
+4: size (4 bytes)
+8: count (4 bytes) -- number of value to name pairs
+12: name_offset (4 bytes) -> UTF-16LE map name (e.g. "LogonType")
+16: N * 8 bytes per entry: { value(u32), name_offset(u32) }
```

### CRIM BMAP Binary Format

```
+0: "BMAP" (4 bytes)
+4: size (4 bytes)
+8: count (4 bytes) -- number of bit to name pairs
+12: name_offset (4 bytes) -> UTF-16LE map name (e.g. "AccessMask")
+16: N * 8 bytes per entry: { bit_position(u32), name_offset(u32) }
```

## 6. What's NOT Covered (Deferred)

| Gap | Impact | Fix Required |
|-----|--------|-------------|
| **BMAP bitwise resolution** | BMAP entries are stored and loaded, but the resolver does a string-keyed `HashMap::get()` lookup instead of bit-testing. Bitmasks like `AccessMask=0x3` (bits 0+1 set) are not decomposed. | Add `match_bitmap()` that decomposes value into individual bits and consults the map for each set bit position. |
| **Provider name scoping in resolver** | All providers' maps are merged into one flat `map_name -> entries` namespace. Two providers using the same map name for different enums cause shadowing. | Add `provider_name` to the resolver cache key. |
| **Pattern maps** | Some providers use pattern-based maps (e.g. wildcards, regex) not discrete VMAP/BMAP entries. Not parsed or stored. | Requires CRIM PMAP block analysis and a separate resolution engine. |
| **Offline/fallback value maps** | Providers with no CRIM data (missing WEVT_TEMPLATE) have no value maps. Values remain raw. | Hand-maintained mapping tables or heuristic inference. |
| **No end-to-end integration test** | Resolver and substitute layers only tested in isolation. No test dumps a real EVTX and verifies enum display names in output. | Add integration test with known-event EVTX samples. |

### Manual Integration

```powershell
# 1. Build
cargo build --release --features dumper -p hotech-evtx

# 2. Dump messages from local system (populates value_maps table)
.\target\release\hotech-evtx.exe dump --msg-dir .\msg-dbs

# 3. Verify value_maps table was populated
sqlite3 .\msg-dbs\hotech-msg-*.db "SELECT COUNT(*) FROM value_maps;"
sqlite3 .\msg-dbs\hotech-msg-*.db "SELECT map_name, entry_value, display_name FROM value_maps LIMIT 20;"

# 4. Parse an EVTX file
.\target\release\hotech-evtx.exe parse .\Security.evtx --msg-dir .\msg-dbs

# 5. Verify: LogonType shows "Interactive"/"RemoteInteractive",
#    boolean fields show "Disabled"/"Enabled", not raw numbers.
```

### Expected Output Characteristics

- `LogonType=2` to `"Interactive"`, `LogonType=10` to `"RemoteInteractive"` (Phase 2+3, CRIM VMAP from WEVT_TEMPLATE)
- `isRoaming=1` to `"Enabled"`, `hasAccess=0` to `"Disabled"` (Phase 1, win:Boolean heuristic)
- `SubStatus=0xc0000072` to `"STATUS_ACCOUNT_RESTRICTION"` (Phase 2+3, CRIM VMAP)
- `Reason=C000005E` to `"No logon servers available"` (Phase 2+3, CRIM VMAP)
- Fields not covered by either layer retain raw string values
- If no messages.db is available, all values remain raw (graceful degradation)
